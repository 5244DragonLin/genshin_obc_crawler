# genshin_obc_crawler：原神观测枢图鉴导出工具

基于纯 Python 标准库调用米游社「观测枢」（原神官方 WIKI）的公开接口，一条命令导出角色、武器、圣遗物图鉴（JSON）与角色图鉴（Markdown），词条封面随产物落盘。

## 💡为什么需要？

- 观测枢词条正文是富文本 HTML，技能倍率表、突破材料、命之座全埋在模板组件里，想按「元素」「星级」「部位」检索只能自己拆
- 接口响应里大量字段是「字符串化的字典/列表」（服务端直接 `str()` 后塞进 JSON），不专门处理拿到的全是转义文本
- 老的词条详情接口只覆盖未迁移的旧词条，新词条请求会报「内容不存在」，需要走新平台接口并统一新旧数据
- 站点随版本更新，想要最新内容就得能随时重跑

**genshin_obc_crawler 解决这些问题**：把字符串化字段还原成结构、把组件模板还原成字段，一次运行落盘成可直接检索的 JSON 与 Markdown。

## ⭐亮点

- **零依赖**：仅 Python 标准库，3.8+ 直接运行
- **直连接口**：读官方 JSON 接口，不渲染页面、不解析 DOM；正文走 hoyowiki 新平台，新旧词条都能取到
- **三类图鉴按信息建模**：角色（天赋倍率表、命之座、突破材料、语音、角色故事）、武器（精炼技能、成长数值、突破材料）、圣遗物（套装效果、五部位名称与故事、搭配推荐）各有固定键名；语音语言按 `voice_languages` 裁剪，突破材料拆成带词条 id 的条目
- **预告词条自动跳过**：站点为未上线角色挂「米提亚【预告】」这类占位词条，正文全是「待更新」，按标题标记识别后直接跳过，不混进图鉴
- **角色双格式**：角色图鉴同时出 JSON 与 Markdown，每人一篇放在 `旅行者/` 下，配 `index.md` 索引表
- **图片本地化**：词条图片随 JSON 落盘，JSON 里给相对路径，离线也能看图。角色封面取词条内的立绘（600×1519 起，多数 750×1900），不使用列表页的 196×196 头像
- **并发抓取**：默认 16 路并发取正文与封面，三类全量从 4 分半降到十几秒；并发数受 `request.concurrency` 控制，填 1 即回到逐条串行
- **增量维护**：按内容指纹对账，没变的条目原样沿用、没变的分类不重写文件，每轮新增/更新/移除都写进 `changes.json`；中断后直接重跑即可，全量重取约 15 秒
- **分类可裁剪**：`--only 角色 武器` 只导指定分类，`--dry-run` 先空跑看清条数，长期只导某几类可在 `catalogs` 段关掉

## 🚀快速开始

### 1. 克隆项目

```bash
# Gitee 镜像（国内访问快）
git clone https://gitee.com/yhl5244/genshin_obc_crawler.git

# GitHub 原仓库
git clone https://github.com/5244DragonLin/genshin_obc_crawler.git

cd genshin_obc_crawler
```

### 2. 安装依赖

```bash
pip install -r requirements.txt   # 仅标准库即可运行，装了 PyYAML 解析配置更稳
```

### 3. 配置文件

复制一份配置，改掉输出目录（不复制也能跑，默认输出到 `output/`）：

```bash
cp config.example.yaml config.yaml
```

### 4. 运行

```bash
# 导出全部三类（角色 / 武器 / 圣遗物）
python src/main.py

# 指定输出目录与分类
python src/main.py --out "E:/BaiduSyncdisk/其他/原神观测枢图鉴" --only 角色

# 先看规模再决定是否落盘
python src/main.py --dry-run
```

## ⌨️CLI 模式

```text
python src/main.py [--out DIR] [--only 分类 …] [--config FILE] [--images|--no-images]
                   [--limit N] [--refresh] [--progress|--no-progress] [--dry-run] [--version]
```

### 输入选项

| 参数 | 说明 |
| --- | --- |
| `--only` | 只导出指定分类，空格或逗号分隔；别名：角色、武器、圣遗物 |
| `--config, -c` | 配置文件路径，默认 `config.yaml` |

### 输出选项

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| `--out, -o` | 产物目录 | 取配置 `output_dir`，缺省 `output` |
| `--images / --no-images` | 是否下载词条图片（角色立绘、武器与圣遗物图标） | 开启 |
| `--progress / --no-progress` | 是否显示进度条；关掉后只打日志 | 开启 |
| `--dry-run` | 只统计条数，不写文件 | `false` |

### 抓取选项

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| `--limit` | 每个分类最多导出几条（试跑） | `0`（不限） |
| `--refresh` | 强制重新抓取，不读本地缓存（缓存关闭时与常规抓取无区别） | `false` |
| `--version` | 打印版本号 | — |

## 📄配置文件

```yaml
# config.yaml
catalogs:              # 抓不抓
  角色图鉴: true
  武器图鉴: true
  圣遗物图鉴: true
output_dir: output
download_images: true
limit: 0
voice_languages:       # 角色保留哪些语言的语音，all = 全部
  - 汉语
request:
  timeout: 30
  retries: 2
  delay: 0.1
  proxy: ""            # 留空 = 绕过系统代理直连
  concurrency: 16      # 并发路数，1 = 逐条串行
cache:
  enabled: false       # 词条原文本地缓存，默认关闭
  dir: .cache
  ttl_hours: 24
logging:
  verbose: false
  progress: true
```

启动时自动读取项目根目录的 `config.yaml`；改名或放别处时用 `--config` 指定。

## ⚙️配置说明

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| `catalogs` | 抓哪几类图鉴，键名写分类名 / 英文键 / 简称都认 | 全开 |
| `output_dir` | 产物目录，相对路径以项目根目录为基准 | `output` |
| `download_images` | 是否下载图片到 `assets/`（角色立绘、武器与圣遗物图标） | `true` |
| `limit` | 每个分类最多导出几条，0 = 不限 | `0` |
| `voice_languages` | 角色保留哪些语言的语音，列表（如 `汉语`、`日语`）或 `all` | `[汉语]` |
| `request.timeout` | 单请求超时（秒） | `30` |
| `request.retries` | 网络异常重试次数 | `2` |
| `request.delay` | 请求间隔（秒） | `0.1` |
| `request.proxy` | 代理地址；留空则绕过系统/环境变量代理直连 | 空 |
| `request.concurrency` | 并发路数，1 = 逐条串行；取值依据见 FAQ | `16` |
| `cache.enabled` | 是否把词条原文缓存在本地；默认关闭，理由见 FAQ | `false` |
| `cache.dir` | 缓存目录，仅在 `cache.enabled` 为真时生效 | `.cache` |
| `cache.ttl_hours` | 缓存有效期（小时），0 = 永不过期 | `24` |
| `logging.verbose` | 打印每次请求明细 | `false` |
| `logging.progress` | 抓取时显示进度条 | `true` |

## ❓️FAQ

**抓取需要登录或 Cookie 吗？**

不需要。两个接口都是公开 GET，本项目没有账号相关逻辑。

**并发开多少合适？会不会把接口打挂？**

默认 16 路，取值来自实测。测法是逐档提升并发（1/2/4/6/8/12/16，再到 24/32/48，最后 64/96），每档取 30~40 个此前未请求过的词条，关掉缓存读取与重试，让限流当场暴露；档间冷却数秒，累计约 560 次请求。

| 并发 | 8 | 12 | 16 | 24 | 32 | 48 | 64 | 96 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 吞吐（条/秒） | 17.8 | 31.4 | 40.3 | 40.1 | 63.0 | 96.1 | 46.6 | 52.6 |
| 平均延迟（秒） | 0.41 | 0.32 | 0.33 | 0.52 | 0.33 | 0.32 | 0.44 | 0.40 |

到 96 路为止没有出现任何失败：没有 429，没有非零返回码，没有连接重置，单条最长 0.86 秒。吞吐在 48 路见顶，64 以上回落到 47~53 条/秒，说明瓶颈此时已经回到本机而非服务端，再往上加只是让请求更密集。据此取 16：全量 453 条约十几秒，同批 60 条（正文加封面）由 22.5~27.0 秒降到 2.1~2.3 秒，对公共接口仍留有可观余量。要更快可调到 32，不建议超过 48；想进一步降低对服务端的压力时填 1，回到逐条串行。

**跑完发现文件没变，是没抓到吗？**

不是。产物按内容指纹比对，站点那边没有改动就不会重写文件。导出到一半中断也不用重来，全量重取约 15 秒，直接重跑即可。要看本轮检查了多少、有没有变化，看日志末尾的「本次变化」一行和产物目录的 `changes.json`。

**为什么默认不开缓存？**

缓存存的是词条正文的原始响应，453 条合计 40.7MB，而建模后的产物只有它的约六分之一。它省的是联网时间：全量 453 条在 16 路并发下，无缓存 15.1 秒、缓存全命中 3.7 秒，11 秒换 40MB 磁盘不值。更关键的是 `ttl_hours` 默认 24 小时且逐条单独计时，每天跑一次时缓存早已过期，一次都不会命中。它真正有用的场景只有一个：调整 `*_model.py` 的解析规则时，原文没变而规则在变，开着缓存可免联网反复重放（3.7 秒一轮）；告一段落后把 `cache.enabled` 改回 `false` 即可。

**角色的封面为什么不是头像？**

词条正文里有一张立绘（`角色展示` 面板），尺寸比列表页的 196×196 头像大一个数量级，所以封面只取立绘，不再下载头像。面板的页签名站点没有统一：老角色写「角色立绘」，新角色写「角色展示」，也有的直接写角色名或「空」「荧」。判定的依据是「列表里唯一的静态图，其余都是技能与待机的 gif」，再按角色名对齐，旅行者靠名字里的「空」「荧」区分两个版本。两个「奇偶」词条没有立绘，`cover` 为 `null`。

立绘按「地址没变且本地文件完好（大于 1KB）」复用，不算 ETag：封面地址里那串 32 位十六进制就是图片内容的 MD5（与响应头 `ETag` 一致，抽查 453 个地址全部吻合），图一换地址就变。同一名字下有多条记录时（旅行者按元素分了 14 条），文件名按元素追加后缀，与 `旅行者/` 下的 Markdown 同名。134 张立绘共约 93MB，最大一张 18MB；不想下载图片可改 `download_images: false`。条目被移除时（如角色正式上线后预告词条消失）封面文件一并清理。

**接口改了字段怎么办？**

接口地址与频道 id 集中在 `src/obc_api.py` 与 `src/exporter.py`，改版时只需调这两处；解析规则对应 `character_model.py` 等三个文件。想强制重新抓取而不比对旧产物时用 `--refresh`。

2. 新建分支：`git checkout -b feature/your-feature`
3. 提交改动，确保 `python -m unittest discover -s tests` 通过
4. 向 `main` 分支发起 Pull Request

## 📋更新日志

### v0.1

首个版本，角色、武器、圣遗物三类图鉴导出为 JSON，角色图鉴另出每人一篇 Markdown。

- 三类图鉴（角色 / 武器 / 圣遗物）按信息建模导出 JSON，角色另出每人一篇 Markdown，封面立绘与图标随产物落盘
- 16 路并发全量约十几秒，按内容指纹增量维护、未变不重写；未上线角色的「【预告】」占位词条自动跳过
